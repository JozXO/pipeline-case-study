Bilingual AI Screening Pipeline

A case study of a solo project: how I planned it, how it scores and filters public job listings in Mandarin and English, how every change is tested, and where a human checks before anything happens.

Soloone person, built with AI coding tools
First monthbuilt in my first month in Taiwan
About 2,400public listings handled a day
2 languagesMandarin and English

The problem

I was job hunting in a new country, in a market where most listings are written in Mandarin. Reading a few thousand listings a day by hand was not possible, and a keyword search on its own returned too much noise. I wanted something that reads public job listings in both languages, sorts them against what I am actually looking for, and leaves every decision to me.

I am a native English speaker, still studying Mandarin. That shaped the design: the pipeline has to translate reliably, and it has to say plainly when it is unsure.

1. How the work was planned

I built this with AI coding tools, so the risk was not typing speed but drift: building more than I needed, or trusting output I had not checked. I used a simple loop for every task:

  • Write a time estimate before starting.
  • Read the start and end time from the system clock, counting only active working time and not time spent waiting.
  • Log the estimate and the actual in one table, with a short note on what was built and what went wrong.
  • Use the log to correct the next estimate.

The log now holds more than 70 tasks. Over the last 20 tasks with both figures, the median actual time was 0.39 of my estimate. In other words my gut guesses ran about two and a half times too high, so I now multiply a gut guess by 0.39 before quoting it. A few examples from the log (minutes, active time only):

TaskEstimatedActual
Make the tests unable to touch live data (isolated copy, hash guard)75about 47
Update the letter writer with new proof rules and checks45about 31
Show a saved letter with no new AI call, plus a rewrite option25about 25

Most tasks came in under the estimate, a few ran over. The log keeps both. Estimates are my own figures written before each task; actuals come from the system clock.

2. How listings are translated, de-duplicated and scored

Translate. Listing titles and descriptions in Mandarin are translated to English so that I can read and compare everything in one language. A machine translation is shown with a visible marker until a checked English version replaces it, and the machine translation never feeds a scoring rule: rules read the original wording. Company names use the official English name where one exists.

De-duplicate. The same job often appears several times: reposted under a new reference, or copied by a recruitment agency. The pipeline compares the company and title, and then how similar the duties are, and leaves out repeats. Left-out listings are logged with the reason and can be restored with one command, so a wrong match is never silent.

Score. Each listing gets a score from 1 to 10 and a verdict (apply, maybe or skip) from written rules, for example: whether the work matches the roles I am targeting, how many years of experience it asks for, whether it needs fluent Mandarin, and whether it is reachable without a car. Some rules cap a score, and some add a short note explaining why. Every score comes with its reasons in plain words, so I can disagree with a specific rule rather than with a number.

3. How changes are tested

A scoring rule that looks sensible can still be wrong, so no change goes in on trust.

  • A held-out test set. I rate a sample of listings by hand and keep them aside. Rules are never tuned on that set, so it shows whether a change helps on listings the rules have not seen. The report gives the average gap between the pipeline's score and mine, and how often the verdicts agree.
  • A real catch. The test set found a listing the pipeline scored 10 that I had rated 3. I traced the cause, fixed the flaw and removed 7 false positives that came from the same flaw.
  • 66 helper tests check the supporting code: reading, writing, validation and the guards around it.
  • 5 regression scenarios run the old and the new version side by side and compare the outputs. A change goes in only when the differences are the ones I intended.
  • Tests cannot damage live data. After one test run wrote fake rows into real files, I made every test run in a scratch copy and added a check that fails if any live file changed.

All of this runs before every change.

4. Where a human checks before any action

  • The pipeline only reads public listings and prepares information. It never submits an application, sends a message or changes my files outside its own folder without me.
  • A high score is a prompt for me to read the full listing, not a decision. Only listings I have read count as checked.
  • Where an AI model drafts something, such as a cover letter, a program checks the draft against written rules (length, banned phrases, repeated sentences, required facts) before it is saved, and I read it before it is used.
  • Anything the pipeline cannot read or is unsure about is marked for me to look at instead of being guessed.
  • Every status change is logged, and every write to the main table is preceded by a backup.

What I would say it shows

  • Planning with real numbers: estimate first, measure, correct.
  • Testing that catches real errors, including my own.
  • Using AI tools with checks around them, and a person who decides.
  • Working across two languages, with Mandarin still in progress.
